## 1. 목적

기존 원가계산서 자동검증 현황 보고서 뒤에 독립적인 후속 기능인 `공고문 초안 생성` 계획을 추가한다. 이 기능은 원가계산서와 사용자가 입력한 발주 정보를 받아 계약유형에 맞는 HWPX 입찰공고문 초안을 생성하는 것을 목표로 한다.

현재 구현 완료로 표현하지 않는다. 보고서에는 `설계 완료 · 구현 예정` 상태로 표시하며, 기존 7단계 검증 흐름과 33개 기능·23개 개선항목 집계는 유지한다.

## 2. 정보 구조

기존 본문 뒤에 다음 내용을 하나의 독립 섹션으로 추가한다.

1. 기능 목표와 현재 상태
2. 상태 태그가 포함된 사용자 흐름 다이어그램
3. 단계별 동작·미동작 상세내역
4. 사용자 입력 항목 전체 목록
5. 계약유형과 조건에 따른 입력 활성화 규칙
6. 1차 구현 범위와 후속 개발 범위
7. 구현 마일스톤과 주요 기술 제약

상단 목차에는 새 섹션 링크를 추가하고, 요약 배지에는 `후속 기능 1개 계획`을 추가한다.

## 3. 사용자 흐름과 현재 동작 상태

사용자 흐름은 다음 순서의 가로 단계도로 보여주고, 좁은 화면에서는 세로로 쌓는다.

`공고문 생성 진입 → 원가계산서 입력 → 자동 채움 → 유형별 정보 입력 → 필수값 확인 → 금액·날짜 확인 → 유형별 템플릿 선택 → HWPX 생성·다운로드 → 한글에서 최종 확인`

각 단계 카드에는 반드시 `동작`, `일부 동작`, `동작 안함` 중 하나의 태그를 붙인다.

- `동작`: 현재 코드와 검증 결과로 해당 단계의 핵심 사용자 목적을 수행할 수 있다.
- `일부 동작`: 화면 또는 엔진 일부는 있으나 필요한 필드·조건·템플릿·종단간 검증이 빠져 있다.
- `동작 안함`: 해당 기능이 구현되지 않았거나 사용자가 완료할 수 있는 경로가 없다.

현재 작업 폴더의 코드와 템플릿 검사 결과를 기준으로 다음과 같이 표시한다.

| 단계 | 상태 | 동작하는 것 | 동작하지 않거나 부족한 것 |
|---|---|---|---|
| 공고문 생성 진입 | 동작 | 첫 화면의 바로가기, `notice` 화면 전환, `?step=notice` 직접 진입, 돌아가기 코드가 있다. | 별도 랜딩이나 진행상태 저장은 없다. |
| 원가계산서 입력 | 동작 | 기존 원가계산서 Excel 업로드와 파싱 흐름을 그대로 사용할 수 있다. 파일 없이 공고문 화면으로 바로 진입할 수도 있다. | 공고문 생성 관점의 입력 안내와 업로드 오류 복구는 별도 정리가 필요하다. |
| 원가계산서 자동 채움 | 일부 동작 | 업로드 파일명에서 사업명 후보를 만들고, 원가계산서 합계 후보를 찾아 추정가격에 넣는 코드가 있다. | 사업소·부서·계약정보·일정 등은 자동 채움되지 않으며 추출 금액의 정확성 확인도 없다. |
| 유형별 정보 입력 | 일부 동작 | 공사·용역·물품 선택과 입찰종류 선택, 공고·금액·일정·담당자 일부 입력란이 있다. | 캡처의 발주계획번호, 발주년월, 세부계약종류, 협정대상 여부, 예산·사급자재비, 수의계약, 품목, 부서별 담당자 등 다수 항목이 없다. 조건별 회색 비활성화도 없다. |
| 필수값 확인 | 일부 동작 | 공사명·발주기관·추정가격 3개가 비어 있으면 생성 버튼을 비활성화하고 누락 항목을 안내한다. | 활성화된 모든 항목을 필수 처리하지 않으며 유형·입찰방법에 따른 필수값 규칙이 없다. |
| 금액 확인 | 동작 안함 | 사용자가 추정가격과 예비가격기초금액을 직접 입력할 수 있다. | 원가계산서 금액과 사용자 입력 금액을 비교하거나 오류를 판정하지 않는다. |
| 날짜·공휴일 확인 | 동작 안함 | 공고일·입찰마감일시·개찰일시를 직접 입력할 수 있다. | 초일 불산입 7일, 공휴일 여부, 다음 영업일 연장 규칙을 검사하지 않는다. |
| 유형별 템플릿 선택 | 일부 동작 | 고정된 HWPX 템플릿 URL을 불러오는 코드와 공사 템플릿 파일이 있다. | 공사·용역·구매 선택에 따라 템플릿을 분기하지 않는다. 현재 템플릿 검사에서는 앱이 아는 14개 자리표시자 중 `입찰종류` 1개만 들어 있다. |
| HWPX 생성·다운로드 | 일부 동작 | ZIP 해제·XML 치환·이스케이프·재압축·다운로드 엔진이 있고, 템플릿 및 fill-test가 통과한다. | 현재 템플릿에 대부분의 자리표시자가 없어 사용자 입력의 대다수가 결과 문서에 반영되지 않는다. 전체 브라우저 다운로드 흐름과 실제 공고문 내용은 아직 인수되지 않았다. |
| 한글에서 최종 확인 | 동작 안함 | 한글에서 열어 확인해야 한다는 안내 문구가 있다. | 생성 파일을 한글에서 열어 서식·문구·값을 확인한 인수 결과가 없다. |

HTML에서는 다이어그램 바로 아래에 위 상세내역을 범주별 카드 또는 표로 배치해, 상태와 근거를 한 화면에서 연결해서 볼 수 있게 한다. 기존 보고서의 초록·주황·빨강 색을 각각 `동작`·`일부 동작`·`동작 안함`에 사용한다.

## 4. 입력과 출력

### 입력

- 원가계산서 파일
- 기본정보: 사업소, 발주계획번호, 발주계획명, 발주년월
- 계약정보: 계약종류, 세부계약종류, 협정대상 여부, 입찰방법
- 금액정보: 예산, 도급자 설치 사급자재비, 발주자 설치 사급자재비
- 수의계약정보: 수의계약 사유, 수의계약 근거
- 품목정보: 대표품목코드, 물품예산금액, 품목수량, 단위
- 담당자정보: 수요부서와 담당자·연락처, 계약부서와 담당자·연락처
- 공고정보: 입찰공고번호, 공고일, 입찰마감일시, 개찰일시, 사업기간, 사업내용

활성화된 입력항목은 모두 필수다. 현재 조건과 관계없는 항목은 화면에서 숨기지 않고 회색 비활성 상태로 남긴다.

### 처리

`원가계산서 + 사용자 입력 → 필수값 확인 → 계약유형별 템플릿 선택 → HWPX 자리표시자 치환 → 파일 무결성 확인`

### 출력

- 계약유형에 맞는 HWPX 입찰공고문 초안
- 브라우저 파일 다운로드
- 사용자가 한글(Hancom Office)에서 열어 최종 확인

## 5. 계약유형별 확장 구조

입력 데이터 구조와 템플릿 선택 구조는 처음부터 공사·용역·구매를 구분할 수 있게 설계한다.

- 1차: 공사입찰공고 템플릿과 HWPX 생성 흐름 구현
- 후속: 용역입찰공고 템플릿 추가
- 후속: 구매입찰공고 템플릿 추가

품목정보는 구매가 아닐 때 비활성화한다. 사급자재비는 공사가 아닐 때 비활성화한다. 수의계약 사유와 근거는 입찰방법이 수의계약이 아닐 때 비활성화한다. 비활성 항목은 필수값 검사에서 제외하고, 활성 항목은 모두 필수 처리한다.

## 6. 1차 범위와 후속 범위

### 1차 구현

- 사용자가 날짜와 금액을 직접 입력하고 수정한다.
- 공사입찰공고용 HWPX 템플릿에 입력값을 치환한다.
- 필수값이 모두 입력된 경우에만 공고문을 생성한다.
- HWPX 생성 실패와 잔여 자리표시자를 사용자에게 알린다.

### 후속 개발

- 원가계산서에서 금액 후보를 추출해 사용자 입력값과 대조한다.
- 공고일은 초일을 산입하지 않고 최소 7일 이상의 입찰공고기간을 확보하는지 검사한다.
- 7일째가 공휴일이면 다음 영업일까지 공고기간을 연장한다.
- 공휴일 데이터를 연동하고 날짜 오류 또는 조정 필요 상태를 표시한다.
- 용역·구매 유형의 전용 템플릿과 항목 규칙을 추가한다.

날짜·금액 검증은 이번 HWPX 초안 생성의 선행조건이 아니다. 보고서에서 1차 생성 기능과 후속 검증 기능을 명확히 분리한다.

## 7. 기술 방향과 마일스톤

1. 화면 연결: 기존 상태 기반 화면 전환에 공고문 생성 경로를 추가한다.
2. 유형별 입력 폼: 캡처의 발주계획 필드와 공고문 전용 필드를 구성한다.
3. HWPX 엔진: HWPX를 ZIP 기반 OWPML XML로 처리하고 `{{자리표시자}}`를 XML 이스케이프된 값으로 치환한다.
4. 템플릿 준비: 공사입찰공고 템플릿을 먼저 준비하고, 동일 인터페이스로 용역·구매 템플릿을 추가할 수 있게 한다.
5. 검증: 잔여 자리표시자, HWPX 재압축 무결성, 브라우저 다운로드와 한글 열기를 확인한다.

템플릿의 자리표시자가 여러 XML 텍스트 run으로 분할되면 단순 문자열 치환에 실패할 수 있다. 템플릿 작성 규칙과 사전 검증 스크립트로 이를 조기에 발견한다. 모든 사용자 입력은 XML 이스케이프를 거친다.

## 8. 시각 표현

기존 보고서의 흰 배경, 절제된 카드, 초록·주황·빨강 상태색과 동일한 디자인 언어를 유지한다.

- 후속 기능 섹션은 기존 본문과 구분되지만 별도 페이지처럼 보이지 않게 한다.
- 입력 항목은 긴 목록보다 범주별 표 또는 그룹으로 정리한다.
- 사용자 흐름은 상태 태그가 붙은 가로 단계도로 표현하고 모바일에서는 세로로 쌓이게 한다.
- 각 단계의 상세내역에서 동작하는 것과 부족한 것을 나란히 비교한다.
- 현재 구현과 후속 개발은 서로 다른 상태 배지와 카드로 구분한다.
- 인쇄 시 표와 단계도가 페이지 폭을 넘지 않게 한다.

## 9. 검증 기준

- HTML 제목, 기존 요약, 기존 7단계 다이어그램과 23개 체크리스트가 보존된다.
- 상단 목차에서 공고문 생성 계획으로 이동할 수 있다.
- 사용자 흐름 모든 단계에 `동작`, `일부 동작`, `동작 안함` 중 하나의 상태 태그가 있다.
- 단계별로 현재 가능한 행동과 빠진 기능이 구체적으로 함께 표시된다.
- 입력항목 전체 목록과 유형별 비활성화 규칙이 빠짐없이 표시된다.
- 공사·용역·구매를 지원하는 확장 구조와 공사 우선 구현 순서가 구분된다.
- 날짜·금액 직접 입력, HWPX 출력, 후속 검증 규칙이 혼동 없이 설명된다.
- 초일 불산입 7일과 공휴일 시 다음 영업일까지 연장하는 규칙이 후속 범위로 명시된다.
- 1440px 데스크톱과 약 390px 모바일에서 가로 넘침 없이 읽을 수 있다.
- 인쇄 스타일에서 새 섹션이 잘리거나 화면 밖으로 넘치지 않는다.
- 실제 구현 완료로 오해할 표현이 없다.
